# Role: Senior Software Engineer — Performance & Architecture Review

You are acting as a **Senior Software Engineer and Performance Architect**.

Your task is to perform a detailed performance review of the existing application, identify bottlenecks, and implement improvements that significantly reduce:

- Application startup time
- Initial library loading time
- Box/folder opening time
- Search response time
- Creation of new boxes
- Saving and updating inventory data
- Image upload time
- Google Drive API latency
- Unnecessary Google Drive API requests
- Perceived UI latency

The goal is to make the application feel **fast and responsive**, while retaining Google Drive as the authoritative persistent storage layer.

Do not redesign functionality unnecessarily. Optimise the existing architecture and user workflows.

---

# 1. Project Context

The application is a **Box Storage / Inventory Management system**.

Google Drive is the underlying persistent storage.

Each storage box is represented by a Google Drive folder containing:

- Inventory JSON/text data
- Item photographs
- Associated metadata

The application provides:

- Docker-hosted backend/API
- Web frontend
- Android/mobile API support
- Google authentication
- Multiple Google accounts
- Library view of storage boxes
- Search
- Box creation
- Box editing
- Item creation/editing
- Image upload
- QR-code lookup
- NFC lookup
- Direct box URLs

Google authentication credentials/tokens **must not be permanently persisted by the server**. The security model defined by the existing project specifications must be preserved.

Google Drive remains the **source of truth**.

---

# 2. Primary Objective

Analyse the existing repository and determine:

> Why does the application take the amount of time it currently takes to start, populate the library, open a box, create a box, upload images, and save changes?

Do not optimise based on assumptions.

First instrument and measure the existing application.

Establish baseline timings before modifying behaviour.

For each important operation determine:

- Total elapsed time
- Frontend processing time
- Backend processing time
- Google Drive API time
- Number of Drive API requests
- Data transferred
- Authentication overhead
- Image-processing overhead
- Serial vs parallel operations
- Cache hits/misses

Produce measurements such as:

    Application initial load:       2.8 s
    Authentication:                 0.4 s
    Library retrieval:              1.9 s
    Drive API calls:                 23
    Open existing box:              1.2 s
    Create box:                     2.4 s
    Save inventory:                 1.1 s
    Upload image:                   3.8 s

Use actual measured results rather than these example values.

---

# 3. Google Drive API Analysis

Pay particular attention to Google Drive interactions.

Inspect the code for:

- Repeated folder listings
- Repeated metadata retrieval
- Sequential API requests
- N+1 request patterns
- Re-fetching unchanged information
- Excessive `files.list` operations
- Excessive `files.get` operations
- Unnecessary full-file downloads
- Unnecessary metadata fields
- Repeated authentication/authorisation work
- Excessive polling
- Image downloads during initial library creation
- Duplicate requests generated by frontend rerenders
- Requests that could safely execute concurrently

For every Drive interaction document:

    Operation
    Drive API endpoint
    Number of calls
    Average latency
    Data transferred
    Whether required
    Whether cacheable
    Whether parallelisable

Reduce Drive API operations wherever this can be done without compromising correctness or the project's authentication/security requirements.

Use partial-field requests where appropriate.

Request only the Google Drive metadata actually required by the application.

---

# 4. Application Opening / Initial Library Loading

Review exactly what happens between:

    User opens application

and:

    User can interact with their storage library.

Identify anything unnecessarily blocking first render.

Consider whether the application can:

1. Render the application shell immediately.
2. Restore appropriate non-sensitive cached metadata.
3. Authenticate.
4. Fetch the minimum Drive metadata required.
5. Display box/library entries.
6. Load thumbnails and secondary information progressively.
7. Refresh changed information in the background.

The application should not require every image or every inventory file to be downloaded before the library becomes usable.

Where appropriate use:

- Lazy loading
- Progressive rendering
- Pagination
- Virtualised lists
- Thumbnail loading
- Request batching
- Controlled parallel requests
- Metadata caching

Optimise both **actual latency** and **perceived latency**.

---

# 5. Opening a Box

Analyse the path from:

    User selects/scans/taps box

to:

    Box contents displayed.

This includes opening through:

- Library selection
- Search result
- QR code
- NFC tag
- Direct URL

QR/NFC/direct-ID access should avoid an unnecessary full-library scan whenever the identifier provides enough information to locate the box directly.

Determine the minimum Drive requests required to display a box.

The initial box screen should prioritise:

- Box identity
- Inventory/item information
- Essential metadata

Images should be loaded progressively unless they are immediately required.

Avoid re-fetching data already available and known to be current.

---

# 6. Box Creation Performance

Profile the complete creation process:

    Create Box
        ↓
    Create Drive folder
        ↓
    Create inventory JSON
        ↓
    Save metadata
        ↓
    Upload images
        ↓
    Update UI/library

Determine which operations are currently sequential and which could safely occur concurrently.

The user should not wait unnecessarily for every secondary operation before seeing the newly created box.

Where technically safe, investigate an approach such as:

    User presses Create
            ↓
    Validate locally
            ↓
    Create required Drive structure
            ↓
    Immediately update UI
            ↓
    Upload/process secondary resources
            ↓
    Confirm successful persistence

However, do not display data as successfully persisted if the required Google Drive operation has actually failed.

Implement clear saving, saved, retry and failure states.

---

# 7. Saving and Editing

Review the current save mechanism.

Determine whether editing a single field results in:

- Full JSON replacement
- Multiple Drive calls
- Metadata re-fetch
- Library refresh
- Image re-fetch
- Other unnecessary operations

Minimise the critical save path.

Where possible, avoid refreshing the complete library after updating a single box.

Update the local application state and refresh only affected resources.

Prevent duplicate save operations caused by:

- Repeated clicks
- UI rerenders
- Race conditions
- Multiple events
- Network retries

Use appropriate debouncing or request coalescing where it improves performance without risking data loss.

---

# 8. Image Performance

Images are likely to represent a significant performance cost.

Analyse:

- Original image size
- Upload size
- Download size
- Browser decoding
- Mobile decoding
- Thumbnail strategy
- Compression
- Concurrent uploads
- Concurrent downloads
- Drive thumbnail support
- Browser caching
- Backend caching

Do not download full-resolution photographs merely to display small library thumbnails.

Determine whether thumbnails can be obtained efficiently or generated/cached without violating the storage architecture.

For uploads, consider client-side image resizing/compression where appropriate while preserving sufficient quality for inventory photographs.

Measure the difference before and after optimisation.

---

# 9. Caching Strategy

Google Drive must remain the authoritative persistent store, but that does not mean every screen interaction must result in a new Drive request.

Design an appropriate cache strategy for **non-sensitive application data**.

Evaluate caching:

- Box IDs
- Folder IDs
- Box names
- Inventory summaries
- File IDs
- Modification timestamps
- Thumbnail references
- Search index information

Potential cache layers may include:

    Browser/mobile memory
            ↓
    Browser/mobile local cache
            ↓
    Backend in-memory cache
            ↓
    Google Drive

Any caching proposal must respect the project's requirement that Google authentication credentials/tokens are not permanently persisted by the server.

Clearly distinguish between:

- Authentication/token storage
- Application metadata caching
- Inventory content caching

Do not weaken the security model simply to improve performance.

---

# 10. Change Detection

Investigate whether Google Drive modification metadata or supported change-detection mechanisms can avoid repeatedly rebuilding the complete library.

The preferred behaviour should be closer to:

    Load cached/indexed metadata
            ↓
    Determine what changed
            ↓
    Retrieve changed records
            ↓
    Update local state

rather than:

    Enumerate every folder
            ↓
    Download every inventory file
            ↓
    Rebuild everything

Use the simplest reliable mechanism appropriate to the application's scale.

---

# 11. Search Performance

Search should not require a complete Google Drive traversal for every query.

Analyse the existing search implementation.

Determine whether an in-memory or local index can safely provide immediate search results based on previously retrieved metadata.

Search should support the existing functional requirements while avoiding unnecessary Drive API traffic.

Document how the search index is:

- Created
- Updated
- Invalidated
- Rebuilt
- Scoped to the authenticated user/session

---

# 12. Frontend Performance

Profile the frontend separately from backend/Drive latency.

Investigate:

- Initial JavaScript bundle size
- Blocking resources
- Unnecessary rerenders
- Large DOM trees
- Image decoding
- Network waterfalls
- Duplicate API calls
- Sequential requests
- Component mounting behaviour
- Search debounce
- Loading indicators
- Skeleton screens
- Route-level lazy loading

The interface should become interactive as early as possible.

Do not hide poor backend performance behind animations. Fix the underlying bottleneck and then improve perceived responsiveness.

---

# 13. Backend Performance

Review:

- API route latency
- Middleware overhead
- Authentication middleware
- Google client creation
- Connection reuse
- JSON parsing/serialization
- Logging overhead
- Synchronous/blocking operations
- Request concurrency
- Memory consumption
- Docker configuration

Determine whether Google API clients or other expensive objects are unnecessarily recreated for every operation.

Do not introduce long-lived authentication persistence in violation of the security requirements.

---

# 14. Concurrency

Identify independent operations currently executed serially.

For example:

    await loadFolder()
    await loadInventory()
    await loadMetadata()
    await loadThumbnail()

Determine whether some operations can safely execute concurrently.

Use bounded concurrency rather than generating uncontrolled parallel Drive requests.

Account for:

- API quotas
- Rate limits
- Retries
- Backoff
- Network congestion

---

# 15. Failure and Retry Behaviour

Performance improvements must not reduce reliability.

Review:

- Network failures
- Drive API errors
- Authentication expiration
- Rate limiting
- Partial uploads
- Duplicate folder creation
- Duplicate inventory creation
- Interrupted image uploads

Retries must be idempotent where possible.

Creating a box must not accidentally create duplicate folders when a network timeout occurs after Drive has successfully processed the original request.

---

# 16. Performance Targets

After establishing the baseline, propose realistic targets.

Where technically achievable, aim for:

| Operation | Target |
|---|---:|
| Application shell visible | < 500 ms |
| Cached library visible | < 1 s |
| Fresh library usable | < 2 s |
| Open cached box | < 500 ms |
| Open uncached box | < 1.5 s |
| Search response | < 200 ms |
| Save normal edit | < 1 s perceived |
| New box usable | < 2 s |
| UI response to user input | < 100 ms |

Do not artificially manipulate measurements to satisfy these targets.

If a target is unrealistic because of Google Drive/network behaviour, document the reason and recommend the best achievable result.

---

# 17. Instrumentation

Introduce structured performance instrumentation where useful.

For example:

    PERF auth                327 ms
    PERF drive.folderList    614 ms
    PERF drive.inventory     281 ms
    PERF library.build       143 ms
    PERF library.total      1041 ms

For Google Drive calls capture at least:

- Operation
- Duration
- Result count where relevant
- Cache hit/miss
- Retry count
- Failure status

Do not log:

- OAuth tokens
- Credentials
- Sensitive authentication headers

Performance logging should be controllable through configuration so verbose diagnostics can be disabled in normal production operation.

# 18. Required Working Method

Work in the following order.

## Phase 1 — Understand

Read:

- Functional specification
- Technical specification
- Existing repository
- Docker configuration
- API implementation
- Web frontend
- Google Drive integration
- Authentication implementation

Do not start by rewriting architecture.

## Phase 2 — Measure

Instrument the existing implementation and produce baseline measurements.

## Phase 3 — Diagnose

Identify bottlenecks and rank them:

    P0 — severe / critical path
    P1 — significant improvement
    P2 — useful optimisation
    P3 — minor optimisation

Estimate expected benefit before implementation.

Example:

    P0
    Library performs 82 Drive API requests.
    Estimated contribution: 3.2 seconds.
    Proposed change: metadata index + parallel retrieval.
    Expected result: 8–12 requests and <1 second.

## Phase 4 — Optimise

Implement improvements incrementally.

Avoid a large rewrite unless measurements prove it necessary.

## Phase 5 — Measure Again

Repeat exactly the same performance tests.

Compare before and after.

## Phase 6 — Regression Testing

Verify that optimisation has not broken:

- Google authentication
- Multiple-account behaviour
- Box creation
- Box editing
- Search
- QR lookup
- NFC lookup
- Image handling
- Direct URLs
- Web client
- Android-facing API
- Security requirements

# 20. Engineering Constraints

Do NOT:

- Replace Google Drive as the authoritative storage system.
- Persist Google OAuth credentials/tokens on the server contrary to the existing specification.
- Introduce an external database merely to hide an inefficient Drive implementation unless there is strong measured justification and it is presented as an architectural recommendation rather than silently introduced.
- Break compatibility with the Android API.
- Change QR/NFC identifiers without migration consideration.
- Sacrifice data integrity for apparent speed.
- report estimated performance improvements as measured results.

Prefer simple improvements with measurable benefit over architectural complexity.

---

# 21. Key Question

At every stage ask:

> "Does the user actually need to wait for this operation before they can continue?"

If the answer is **no**, remove it from the critical path where safe.

The desired result is an application that opens quickly, displays useful information immediately, accesses Google Drive efficiently, and makes creating, opening, editing and saving storage boxes feel effectively instantaneous wherever network and Google Drive latency permit.
